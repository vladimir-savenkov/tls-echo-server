# TLS Echo Server

Асинхронные TLS echo-сервер и клиент на C++17 с бинарным протоколом и CRC32.

## Особенности

- **Протокол:** заголовок с ID, длиной и CRC32, затем данные пакета.
- **Соединения:** TLS через OpenSSL, асинхронный ввод-вывод через Boost.Asio;
  `TCP_NODELAY` на обеих сторонах, чтобы алгоритм Нагла не добавлял паузы
  в измеряемые задержки.
- **TLS-версии:** пол 1.2, потолок открыт — negotiate доходит до TLS 1.3
  и выше, поддерживаемых OpenSSL (1-RTT handshake).
- **Нагрузка:** несколько TLS-соединений на общем пуле потоков; число пакетов
  или длительность прогона, бинарные данные заданного размера, throughput и p50/p95/p99.
- **Проверка ответов:** совпадение ID, CRC32 и полезной нагрузки байт в байт.
- **TLS:** проверка цепочки доверия и имени сервера включена по умолчанию.
- **Лимиты:** таймауты операций, ограничение активных соединений и размера данных.
- **Журнал:** spdlog; на уровне `debug` видны состояния асинхронных операций,
  номера пакетов и их данные.
- **Завершение:** сервер обрабатывает SIGINT и SIGTERM, давая сеансам время закончить.

## Технологии

- C++17
- Boost.Asio, Boost.Program_options
- OpenSSL
- spdlog
- CMake

## Сборка и тесты

На Ubuntu установите зависимости:

```bash
sudo apt-get update
sudo apt-get install build-essential clang cmake ninja-build openssl python3 \
  libboost-all-dev libssl-dev libspdlog-dev
```

Из корня проекта:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
```

Исполняемые файлы: `build/server` и `build/client`. Для оптимизированной сборки
используйте отдельный каталог:

```bash
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release --parallel 2
```

## CI/CD

GitHub Actions запускает CI при push в `master`, для pull request в `master` и
вручную через `workflow_dispatch`. CI собирает Debug-версию с GCC и Clang и
запускает C++ тесты. Отдельная задача Windows проверяет MSVC с vcpkg. Отдельные сборки с AddressSanitizer (ASan) и
ThreadSanitizer (TSan) также запускают тесты, затем поднимают TLS-сервер,
передают 100 пакетов через 20 соединений клиента и проверяют завершение сервера
по SIGTERM. ASan проверяет ошибки памяти и утечки при выходе процесса;
TSan проверяет гонки данных. Эти проверки выполняются в разных процессах и
сборках: ASan и TSan не включаются одновременно.

Отдельная задача MemorySanitizer (MSan) проверяет чтение неинициализированных
данных в коде пакетов и CRC32, запуская `tests/test_packet.cpp`. Для неё CI
собирает инструментированную libc++ из исходников LLVM 18.1.8 и кеширует
результат. Системная библиотека C++ без инструментирования даёт ложные
сообщения MSan. Сервер и клиент в MSan-задачу не входят: для достоверной
проверки их пришлось бы также собрать с MSan все сторонние библиотеки,
включая Boost, OpenSSL и spdlog. ASan и TSan продолжают проверять оба бинарника.

Локально можно повторить проверки (нужны Clang и OpenSSL CLI):

```bash
cmake -S . -B build/asan -G Ninja -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_COMPILER=clang++ \
  '-DCMAKE_CXX_FLAGS=-fsanitize=address -fno-omit-frame-pointer' \
  -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=address
cmake --build build/asan --parallel 2
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 ctest --test-dir build/asan --output-on-failure
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 python3 scripts/sanitizer_smoke.py build/asan

cmake -S . -B build/tsan -G Ninja -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_COMPILER=clang++ \
  '-DCMAKE_CXX_FLAGS=-fsanitize=thread -fno-omit-frame-pointer' \
  -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread
cmake --build build/tsan --parallel 2
TSAN_OPTIONS=halt_on_error=1:exitcode=66 ctest --test-dir build/tsan --output-on-failure
TSAN_OPTIONS=halt_on_error=1:exitcode=66 python3 scripts/sanitizer_smoke.py build/tsan
```

Для локального запуска MSan после сборки инструментированной libc++ используйте
`bash scripts/msan_packet_test.sh /путь/к/msan-libcxx`. Команды сборки libc++
приведены в задаче `memory-sanitizer` файла `.github/workflows/ci.yml`.

## Как запустить

1. Соберите проект по инструкции выше и сгенерируйте самоподписанный сертификат:

   ```bash
   bash scripts/generate-certs.sh
   ```

2. Запустите сервер:

   ```bash
   ./build/server --cert server.crt --key server.key
   ```

Сервер по умолчанию слушает порт `8443` и использует 4 рабочих потока. Для
вывода всех аргументов и значений по умолчанию запустите `./build/server --help`.

Для остановки нажмите `Ctrl+C` (SIGINT) или отправьте SIGTERM. Сервер прекращает
принимать новые соединения и ждёт завершения активных сеансов до 5 секунд. Если
сеансы не закончились за это время, сервер закрывает их сокеты, обрабатывает
отменённые операции и выходит. Повторный `Ctrl+C` или SIGTERM закрывает все
сеансы немедленно, не дожидаясь таймаута. При обычном закрытии соединения
выполняется TLS shutdown.

## Нагрузочная проверка C++ клиентом

```bash
./build/client --host localhost --port 8443 --cert server.crt \
  --clients 100 --threads 4 --packets 20
```

`--clients` задаёт число одновременных TLS-соединений (по умолчанию 1),
`--packets` — число запросов на каждом соединении (по умолчанию 5), а
`--threads` — число потоков общего цикла обработки событий (по умолчанию 1).
Порт по умолчанию — `8443`; `--host` обязателен. Все аргументы показаны в
`./build/client --help`.
После завершения клиент выводит число успешных соединений и ответов; при
ошибках возвращает ненулевой код выхода. Для подробного журнала добавьте
`--log-level debug`.

### Сертификаты и таймауты

Клиент по умолчанию проверяет цепочку сертификата через хранилище доверия OpenSSL
и соответствие имени сервера DNS/IP в сертификате. На Windows хранилище OpenSSL
не обязательно совпадает с системным хранилищем Windows; при необходимости
передавайте файл доверенных CA через `--cert`.
Для локального самоподписанного сертификата укажите `--cert server.crt`.
Явное отключение проверки: `--insecure`; этот параметр несовместим с `--cert`.
Каждое соединение CLI имеет отдельный TLS-контекст и trust store: это исключает
конкурентный доступ к ленивым X509-кешам системной OpenSSL 3.0 при верификации.
Контексты настраиваются до начала измерения прогона. Если вы используете классы
напрямую, также передавайте отдельные контексты для параллельных проверяемых
соединений (см. [описание аналогичного отчёта TSan](https://github.com/python/cpython/issues/150191)).
Клиент передаёт SNI для DNS-имени. Скрипт генерации сертификата включает SAN для
`localhost` и `127.0.0.1`.

`--timeout-ms` (по умолчанию 10000) ограничивает каждую операцию отдельно:
у клиента DNS, TCP connect, TLS handshake, запись, чтение заголовка/данных и
TLS shutdown; у сервера handshake, чтение заголовка/данных, запись и shutdown.
По истечении срока сокет закрывается; клиент сообщает этап ошибки и завершает
работу с кодом 1. Таймаут не сбрасывается при получении отдельного байта
внутри одной операции чтения. Разрешение DNS зависит от системного resolver:
его фоновая работа может закончиться позднее уведомления о таймауте.

### Лимиты сервера

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `--max-connections` | 1024 | Максимум принятых активных сессий, включая handshake |
| `--max-payload` | 65535 | Максимум байт полезной нагрузки (0 — только пустые пакеты) |
| `--timeout-ms` | 10000 | Срок отдельной сетевой операции, мс |
| `--shutdown-timeout-ms` | 5000 | Срок завершения активных сессий после сигнала, мс |

Избыточные соединения закрываются до TLS handshake. Превышение размера
отвергается сразу после заголовка, до выделения буфера данных. При выходе
сервер выводит счётчики принятых и отклонённых соединений, таймаутов,
превышений размера, ошибок accept, эхо-пакетов и их полезных байт,
а также оставшихся активных сессий. Счётчики эха (только полностью
записанные ответы, без заголовков) позволяют сверять throughput клиента
с серверной стороной. Лимит действует на процесс;
очередь TCP ОС и память TLS в него отдельно не входят.

### Прогон по времени и метрики

```bash
./build/client --host localhost --cert server.crt --clients 20 --threads 4 \
  --duration 10 --payload-size 4096
```

`--payload-size` задаёт бинарную нагрузку от 0 до 65535 байт; без него отправляется
текст `Hello from C++ Client, packet #N`. Временной режим `--duration` задаётся
целым числом секунд для каждого соединения, начиная после handshake, и
несовместим с явным `--packets`. По завершении срока заканчивается текущая
пара запрос/ответ, затем TLS shutdown. Общая длительность также включает
установление соединений и их закрытие; зависшие операции ограничены таймаутами.

Клиент показывает пакеты/с и MiB/с возвращённых полезных данных за полное время
прогона (без заголовков и TLS overhead), а также p50/p95/p99 отдельно для
запросов и для DNS + TCP + TLS. Задержка запроса измеряется от начала записи
до полной проверки ответа. Гистограммы содержат 512 интервалов на соединение;
квантили — верхние границы интервалов с погрешностью до 9.1% для задержек
от 1 мкс. Значения ниже 1 мкс попадают в первый интервал. Память статистики
не растёт с длительностью прогона. Успешный обмен пакетами и завершённый
TLS shutdown учитываются отдельно: ошибка shutdown делает соединение неуспешным,
но уже проверенные пакеты остаются в счётчиках.

На обеих сторонах соединения включён `TCP_NODELAY`: без него алгоритм Нагла
придерживает хвостовые сегменты записи до подтверждения (ACK), а delayed-ACK
партнёра добавляет паузы до 40 мс на Linux и до 200 мс на Windows — они
попадали бы в хвосты p95/p99 и не отражали бы работу самого сервиса.

### Что проверяют тесты

Пять программ CTest проверяют кодирование и граничные размеры пакетов,
ошибки транспорта, точность echo и единственное уведомление о завершении,
фрагментированные TCP-ответы, экранирование журнала и реальный TLS на loopback.
TLS-тесты включают доверенный/неизвестный/просроченный сертификат, неверное имя,
зависания handshake/чтения/записи/shutdown, лимиты сессий и данных, принудительное
завершение сессий и многопоточную работу с пустыми и максимальными пакетами.
Сертификаты создаются в памяти, порты выделяются автоматически. Тестовые
клиенты подключаются к loopback `127.0.0.1`: wildcard `0.0.0.0` используется
для прослушивания, но не подходит как адрес назначения connect в Windows.

### Windows / Visual Studio

При установленном vcpkg задайте `VCPKG_ROOT` и используйте существующие
пресеты `windows-x64-debug` / `windows-x64-release` (из терминала разработчика
с Ninja), либо откройте каталог в Visual Studio. Пресеты требуют CMake ≥ 3.20.

```powershell
cmake --preset windows-x64-debug
cmake --build --preset windows-x64-debug
ctest --preset windows-x64-debug
```

Манифест vcpkg явно устанавливает `boost-asio`: пакеты `boost-system`,
`boost-thread` и `boost-program-options` не гарантируют наличие заголовков Asio.
CMake задаёт MSVC параметры `/utf-8` и `/EHsc`; поддержка исключений сохраняется
также при переопределении `CMAKE_CXX_FLAGS` в CI с `/W4 /WX`.
Для всех целей определён `BOOST_ASIO_NO_DEPRECATED`, чтобы Linux-сборки также
выявляли использование удалённых API Asio. Таймеры отменяются через `cancel()`
без аргумента `error_code`, совместимый со старыми и новыми версиями Boost.

Преобразования сетевого порядка байтов находятся в `include/wire.h` и не требуют
POSIX/Winsock. Генерация сертификатов
через `.sh` требует Bash и OpenSSL CLI; C++ TLS-тесты не требуют этих утилит.

## Журналирование

По умолчанию сервер пишет в `server.log`, клиент — в `client.log`; уровень
журнала — `info`. Пути и уровень можно задать через `--log-file` и
`--log-level`. Например, в разных терминалах:

```bash
./build/server --cert server.crt --key server.key \
  --log-level debug --log-file server-debug.log
./build/client --host localhost --cert server.crt --clients 2 --packets 3 \
  --log-level debug --log-file client-debug.log
```

Очередь асинхронного журнала (8192 сообщений, один фоновый поток) использует
политику `overrun_oldest`: сетевые потоки никогда не блокируются на
журналирование, но при переполнении очереди теряются самые старые
debug/info-записи. Файл сбрасывается на диск при уровне `warn` и выше,
поэтому предупреждения и ошибки в файле присутствуют даже после потерь.

На уровне `debug` записываются запуск и результат асинхронных операций,
состояния клиента, порядковый номер и данные каждого отправленного и полученного
пакета. Непечатные байты данных экранируются. Учитывайте, что журнал на этом
уровне содержит содержимое пакетов. Сообщения сервера о сессиях помечены
идентификатором сессии и адресом удалённой стороны (`Session 2 (127.0.0.1:43378)`);
это же обозначение появляется в предупреждениях об ошибках, таймаутах и
превышении лимитов.

## Python-утилиты

Параллельная проверка нескольких TLS-соединений:

```bash
python3 scripts/multi_client_test.py --host localhost --port 8443 \
  --clients 10 --messages 5 --insecure
```

Интерактивный клиент:

```bash
python3 scripts/interactive_client.py --host localhost --port 8443 --insecure
```

`--insecure` предназначен только для локальной проверки. Для проверки
сертификата передайте CA или самоподписанный сертификат сервера:

```bash
python3 scripts/interactive_client.py --ca-cert path/to/server.crt
```
